3. 总控先写本批次计划和普通进度记录，再自主执行；无需在计划写完、第一候选完成、跨网站切换时逐次请求确认。现有授权不包括安装付费服务或对外发布。
4. 中断后回到同一个总控任务发送：“继续执行 `construction_pipeline/prompts/expand_10_tasks.md`；先读取 `construction_pipeline/ten_task_phase/` 的计划、账本和进度，接续未完成工作，沿用累计预算，不重复已完成运行。”

跨网站生产入口尚需适配，因此此处不提供一条看似现成、实际会落到旧campaign的批处理命令。准备工作属于执行prompt的范围，由总控完成并留下真实命令与恢复入口。

## 本阶段交付标准

每个计入10题的底题必须满足：

- 来自原50题的12个生态之一；真实来源、稳定时间/版本、有界候选集合、明确且唯一可核验的答案。
- 具有论文要求的实际检索依赖；说明前步证据怎样改变后续查询、过滤或分支，并保存忽略该依赖会改变结果的真实反例。允许API、批量下载和本地代码，不要求唯一点击路径。
- 若固定少量下载已取得全部决策字段，后续仅剩本地计算或过滤，不得把这些步骤计为检索依赖；按扩展规划核查合法简化路径是否消除了所声称的关键依赖。
- CG/GO语义等价，共享答案和输出规则；GO可以省略解法，不能省略必要条件。以英文任务为主，中文记录研究过程。
- 参考程序从保存的源证据计算答案，核心聚合/连接有第二条独立核对路径；逐字段证据、候选全集和纳排依据齐全。
- 开发阶段完成CG/GO各两次普通Sol盲解、各一次Sol捷径攻击，以及GPT-6证据审计。每个会话独立隔离，实际模型核验成立。
- 两种题面分别出现至少一次可复查的实质性错误，例如领域定义、身份、范围或检索决策错误；两份都完整正确的题面不足以满足本阶段困难筛选目标。只有数值文本排序、抄录、漏列、访问失败或零有效进展不能单独作为入选理由。错误仍原样记录，不人为改分。
- 定稿版本的CG与GO分别完成3次预定的新Sol/medium普通求解，分别计算未四舍五入的Item-F1均值；只有两个均值都严格低于0.70且无未解决NA/运行异常，才计入10个收录底题。不能用任一次最低分、CG/GO合并平均或整个题集均值替代。

以上是本阶段采用的开发筛选口径，不是论文规定的成功率阈值，也不是单题统计上的难度证明。每候选最多2次实质修订；修订后重新执行受影响的参考计算与盲解，不混用不同版本成绩。没有真实机会时及时淘汰、补充候选，不能做完10个候选就宣告完成。

优先争取覆盖4—5个生态、至少5种构造方法；同一依赖结构仅换实体/年份的家族最多计2个底题。先探索ChemExpo、KEGG、Reptile、WQP、Water Office；允许依据来源可达性和实际反例，在原12生态内调整。网站名额不硬性锁定，也不靠同模板大量改写补齐数量。

## 模型分工与执行方式

| 工作 | 模型 | 可见材料 |
| --- | --- | --- |
| 网站探索、设计、参考解、配对、审计、裁决、必要修订 | GPT-6 Astra/high | 该角色需要的构造材料与证据 |
| 普通盲解、捷径攻击、收录复测、新旧对照求解 | GPT-5.6 Sol/medium | 单个公开题面、输出规则、统一日期和统一工具 |

构造可分配独立子任务，材料与资产在控制端汇总。正式盲解须通过已有实际读取隔离启动，不能从总控或构造者对话fork，也不能靠一条“请忘记答案”的指令充当盲测。所有实际工作会话纳入同一批次账本与预算；不通过账本外的子任务隐藏成本。

先完成参考解与题面，再做CG/GO各一次A盲解；值得继续才补B盲解、CG/GO攻击与审计。A计入两份普通盲解之一，避免重复启动名称不同但内容相同的筛选。收录复测与普通求解使用同一公开提示，求解者须尽力答对，看不到70%阈值、难题目标、参考网站画像、oracle或失败提示。

## 启动前要补齐的最少实现

复用现有工具与已验证机制，不重新做arxiv旧题或WQP固定版本的完整闭环。下列问题已在2026-09-09只读审查中确认：

1. `wqp_single/runtime/run_batch.py`没有透传 `--campaign/--ledger`，`run.py`默认的旧WQP批次和原Sol批次都已结束。新批次须明确传入自己的计划和账本；不修改旧批次的结束标记。
2. 旧批处理仅按输出目录存在跳过。恢复应检查实际运行状态和交付资产，区分完成、失败、未启动与中断；保留原失败目录，按普通新attempt记录必要重试，不覆盖历史结果。
3. `run.py`虽接收 `--schema`，最终仍强制解析求解者四字段。非盲阶段需要按自己的stage schema解析，并能实际生成、回收和验证参考程序等资产，不能只改schema参数就当接通生产链。
4. `stage_registry.json`仍是设计规格；旧 `audit_run.py`也绑定旧批次。按本阶段所需接入工作单、角色、输入可见范围和输出回收，不把注册表存在当成可执行流水线。
5. 下载工具目前仅支持WQP/EPA相关域名，镜像与数据工具也是WQP用途。补所需官方读取能力，所有新旧盲测使用同一批次工具配置，保留现有域名、重定向、大小和文件隔离保护，不按单题注入网站入口或专用解题函数。
6. CSV再导入为TEXT的行为须明确；用中性数据检查往返及表格交付。改动工具类型或解析行为必须对新旧一致采用新协议版本，不回改已有Sol结果。

检查这些实际行为后继续构造，不停在输出实现计划。只对有实际改动和风险的环节做必要验证；不重复大量旧模型运行作为工程检查。不新增hash、冻结契约或额外通行机制。

## 逐题收录复测与70%条件

不必等凑齐10个候选才测试。每个候选版本开发验证完成后，先在普通测试计划中登记版本、工具、评分规则、CG/GO各3次试次、有限环境修复规则和停止条件，再执行6次全新Sol/medium普通求解。会话独立于开发，不能混入开发A/B成绩或捷径攻击成绩；完整执行预定试次，不因前面低分提前结束。

使用现有确定性评分规则的原始Item-F1：CG_mean=(CG_1+CG_2+CG_3)/3；GO_mean=(GO_1+GO_2+GO_3)/3。所有数值须有效且在0—1范围。**只有CG_mean<0.70且GO_mean<0.70，同时通过内容、SGR结构与实质性错误审计，才收录该底题及两个题面。** 恰好0.70也不收录。判定使用完整精度，不用展示时的百分数舍入值；允许某一次高于70%，但不宣称模型每次或未来都一定低于70%。

有未解决NA、解析失败、环境故障或不足3次时暂不收录，不补零、不缩分母、不追加抽样凑出低分。仅真实基础设施故障可按事前记录的有限规则修复重试，保留原运行；模型解错或漏列不属于环境重试理由。

将条件落实到普通候选收录和导出检查，逐题核对6个预定run_id、同一版本、实际模型/effort、有效分数、两个均值和审计结果。用边界样例验证0.70不通过、任一题面不达标不通过、缺失/混版本/选低分不通过；不新增复杂验证框架。

Item-F1可由原评分计数表示为精确比例 `2×正确字段数/(参考字段数+预测字段数)`，三次均值再与7/10比较，避免二进制浮点误差把恰好70%误判为低于70%。报告展示值可以舍入，收录判定不可用舍入后的值。

每个题目/评测协议版本只安排一轮收录复测，因实质修改产生新版本才重新执行完整6次。不得对未变题目反复测到低分，或把多个版本最低试次拼成一组。未通过的候选淘汰或在2次实质修订范围内改进，再按证据与预算补候选直到收录10题。

本规则会使用复测结果选择题目，最终十题的这些分数属于筛选条件下的成绩，不能称为无偏最终评估。独立会话不等于独立于数据选择。真正未用于筛选的评估留待后续明确安排，本阶段不额外增加循环“再确认”。10个成功收录底题至少需要60次收录复测；未通过版本的复测也计入预算。

旧近邻在查看新题筛选分数前指定对应关系，从中预先选最多5道可核验旧题做同配置比较，每题CG/GO各3次，最多30次。共享同一旧题只测试一次这组试次，不复制成多份独立对照；不重跑全50题。旧题的成绩不替代或改变绝对70%收录条件。

已有waterquality_004存在公开答案暴露和选站歧义，不再作为唯一标尺。旧对照若暴露答案或语义不唯一，原成绩保留并单列，不能静默删掉、补跑或改oracle后继续称原题。缺少可信对照时如实报告比较范围与不确定性，不自动另造一批对照扩大任务。

报告Item-F1、Row-F1、完整正确率、CG/GO分项、实际分母与错误类型；只有Item-F1用于70%判定，其他指标辅助解释。解析失败与环境失败按事先约定处理，不用零或修正后的中间答案填补原NA。

逐题通常保持 `content_validated`，难度按证据写 `screened`、`inconclusive` 或其他实际状态。现有schema中 `auto_validated`要求该题自身已有充分的 `confirmed_harder`证据，不能因为集合低分或3次测试就批量填写。人类审查保持实际状态；自动审计不冒称专家已审核。

## 建议预算与停止点

以下为发送启动prompt时采用的默认建议，用户可在发送前调整：

| 项目 | 上限 |
| --- | ---: |
| 本阶段累计模型工作会话，包含构造、盲测、攻击、审计、对照、失败与重试 | 300次 |
| 本阶段累计执行墙钟，跨恢复继续累计 | 48小时 |
| 同时运行的工作会话 | 4个 |
| 每次运行 | 6000秒 |
| 每次无实质进展 | 3000秒 |
| 每候选实质修订 | 2次 |

300次是停止边界，不是目标用量或保证完成的承诺。按5网站、10候选全部一次通过质量和70%条件，开发为115次，十题收录复测60次，5道旧题复测30次，合计205次，尚无淘汰与修订。若20候选中10个进入完整复核且全部一次通过收录复测，简化估算为255次，余45次处理额外探索与修订。因而不沿用旧120次上限。低于70%的条件可能显著增加淘汰量，本阶段尚无可预测接受率。

开发期间为尚未完成的每个收录复测候选预留6次及已选旧对照所需次数，避免把预算全部花在找题后声称“仅缺复测”。已淘汰版本的6次也实际消耗预算，不能仅按最终10题计费。普通离线计算不计模型调用；任何实际启动的模型工作会话都计入。恢复不重置累计会话或执行用时。

取得10个同时满足质量与70%条件的底题并完成规定对照后交付；预算/额度耗尽或必要外部条件阻塞时保存现状、说明已完成数量与剩余工作。未满10题就是数量目标未完成，不能把未达阈值题目放入成功导出。没有必要在每个候选或网站切换时请求用户确认。

## 交付位置与操作入口

本批次运行时统一使用 `construction_pipeline/ten_task_phase/`；若发现该目录已有本阶段工作，先读计划和状态再接续，不覆盖或重复初始化。

- `campaign.json`、`session_ledger.jsonl`、`progress.md`：实际参数、累计用量、已验收数量、候选状态、下一步。
- `candidates/`、`runs/`：成对题面、共享oracle/规则、证据、参考程序、模型输入输出、评分、审计和修订记录。
- `comparisons/analysis_plan.json`与收录报告：先记录的逐版本试次与分析方法、全部收录复测和旧题对照成绩；逐题列出CG/GO各3次Item-F1、两个均值、审计与收录结论。
- `exports/constraint.jsonl`与`exports/goal.jsonl`：成功完成时各10条；不足则明确标部分交付，不能重复/伪造凑满。文件格式与原发布数据兼容。
- `report.md`：逐题研究需求、网站、构造方法、相对旧题升级、证据完整性、CG/GO成绩与70%判定、失败与不确定性、实际成本和后续建议。明确此批分数参与了收录筛选，不冒称无偏评估。
- `README.md`：本批次真实可执行的启动、恢复、离线重算与验证命令；这些命令须完成适配后实际核验，不能提前编造。

完成条件是可查看的数据、证据、原始运行与诚实的难度结论，不是调度器运行成功。原始WQP/GPT-6/Sol实验保留；本阶段不自动扩到50新题、不发布或建立后续自动运行。
