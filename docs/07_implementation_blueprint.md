# 全 GPT-6 构造流水线：执行蓝图

2026-09-09更新：本文保留最初全GPT-6方案。当前已有WQP实际隔离运行、评分与Sol复测；后续模型分工、首批范围及尚需补齐的实现，以[扩展计划](08_scale_plan.md)为准，不重复启动旧题闭环。

2026-09-08。本文细化现有方案的实现顺序和研究判断。它是实现规格；尚未启动新题批量构造或取得新题难度成绩。

## 1. 总体选择

所有需要语言理解、浏览决策、任务设计和证据审查的角色都使用 **Codex + gpt-6-astra**。Python/SQL 负责调度、记录、集合运算和评分。一个控制程序调用不同阶段的全新 Codex 会话，形成循环；不需要引入另一套 agent 框架，也不把所有材料交给一个长会话反复自我确认。

构造过程允许探索分支和失败。**产出单位是有证据支持、语义明确的底层任务及其 CG/GO 两种表达**。网站名额、候选数、调用数都不是必须产出多少合格题的承诺。

目前已有 11 份阶段提示词、任务/阶段/求解/裁决的 4 份 schema、阶段注册表，以及公开题面投影和候选一致性检查工具。最需要补的实现是：实际隔离的工作进程、任务资产交接、确定性评分和新旧题对照。先用现有网站做一个完整闭环，再逐步增加网站覆盖。

## 2. 三类工作分开

| 工作 | 目标 | 允许输入 | 产物 |
| --- | --- | --- | --- |
| 构造与充分取证 | 得到真实且可解的问题 | 旧题、网站画像、候选私有定义、官方资料 | 参考解、证据、候选全集、纳排账本、CG/GO |
| 独立内容验证 | 找出答案错、题面歧义、遗漏、无效依赖 | 先仅公开题面；交卷后审计者可看全部材料 | 独立答案、反例、审计与修订建议 |
| 难度试验 | 在指定 GPT-6 系统下比较新旧题 | 相同公开输入格式、相同工具/预算 | 原始作答、逐题分数、对照差值与不确定性 |

内容验证可以给两位独立求解者更充分的预算，但**不能给答案提示后仍称为盲解**。难度试验单独使用统一配置。一个候选可以通过充分预算的可解性验证，同时在受控难度预算下经常失败；二者没有冲突。

两名 GPT-6 求解者的一致只是线索。必须同时用官方记录、完整性依据和可重算程序支撑真值。自动阶段可自主完成；如论文保留三轮人类专家验证的描述，应在最终研究材料中完成对应的人类工作，或如实说明方法已改为自动构造与验证。

## 3. 单题循环及明确交接

顺序为：**探索 → 设计 → 参考解 → 成对题面 → 盲解/攻击 → 审计 → 裁决 → 难度筛选 → 最终确认**。提示词文件的数字是标识，不是排序程序。

| 阶段 | 必要输入 | 必须写出的主要资产 | 后继 |
| --- | --- | --- | --- |
| `01_site_explorer` | 一个已有生态、正式旧近邻、允许请求与预算 | `site_profile.json`, `opportunities.json` | 有实证机会才设计；零机会也是合法结论 |
| `02_candidate_designer` | 已观察机会、旧近邻 | `candidate.json`, `state_graph.json`, `design_rationale.md` | 未验证条件留待查，不填 oracle |
| `03_reference_builder` | 候选、原始资料 | 源响应、完整候选集、纳排账本、逐字段证据、参考程序、oracle、反事实 | 程序从保存原始材料实际运行成功 |
| `07_pair_writer` | 同一规范化任务定义与 oracle | `cg.json`, `go.json`, `pair_alignment.json` | 公开题面不得靠私有 rubric 补必要条件 |
| `04_blind_solver` | 每次仅一个公开题面 | 独立 `result.json` 与工具事件 | 内容验证默认 A-CG、A-GO、B-CG、B-GO 四次独立会话 |
| `05_shortcut_attacker` | 每次仅一个公开题面 | 尝试的实际答案、路径与来源 | 默认 CG/GO 各一次；不能只写“可能存在捷径” |
| `06_evidence_auditor` | 全部候选与参考、四份盲解、攻击、确定性评分 | `content_audit.json`, `audit_report.md` | 原始证据高于作者解释和票数 |
| `08_adjudicator` | 审计、未决项、预算 | `decision.json` | 修订、淘汰、不可判断或进入难度测试 |
| `09_repair` | 明确问题与受影响资产 | 新 revision、修改与重跑范围 | 回到参考解；语义变化后重做盲解 |
| `10_confirmation_solver` | 与 04 完全相同的公开输入和提示 | 新旧题的确认作答 | 父进程评分与统计，求解者不知道难度目标 |

`00_controller` 只用于需要研究判断的排程，例如选择机会、解释失败后换方向。普通程序负责已确定的阶段次序、预算扣减和结果检查，不必为了“更 agentic”每次文件复制都调用 GPT-6。

所有非盲阶段最终回复使用 stage_result schema；candidate schema 约束写出的 `candidate.json`，decision schema 约束裁决资产 `decision.json`，二者均不是该阶段最终回复。盲解、攻击、确认最终回复使用 solver_result schema。阶段摘要 `completed` 只表示该项工作完成，不表示题目通过验证。

## 4. 普通工作单和文件交接

控制程序应构造如下普通 JSON 工作单；下例是设计示例，不代表已有候选通过任何环节：

```json
{
  "run_id": "run_000021",
  "candidate_id": "wqp_panel_001",
  "revision": 1,
  "stage": "03_reference_builder",
  "purpose": "construction",
  "variant": null,
  "replicate": 1,
  "input_assets": [
    {"asset_id": "candidate", "path": "candidates/wqp_panel_001/r01/candidate.json"},
    {"asset_id": "site_profile", "path": "sites/WATER_QUALITY_PORTAL/site_profile.json"}
  ],
  "output_assets": ["reference_report.md", "source_manifest.json", "reference/oracle.psv"],
  "model": "gpt-6-astra",
  "effort": "high",
  "tool_profile": "construction_research",
  "max_wall_seconds": 6000,
  "remaining_campaign_calls": 98
}
```

工作单留在控制端。输入资产路径相对 campaign 根；每次复制到工作目录的 `inputs/`，生成资产 ID 到工作目录相对路径的映射。模型写出的 artifact 路径相对该次工作目录。控制端只接收目录内实际存在的普通文件，拒绝越界路径和指向其他目录的符号链接，然后复制回候选目录；控制端更新 candidate 中的路径引用。不要把多个角色的原目录当作共享可写工作区。

盲阶段使用更窄的接口：模型仅收到 `instruction / output_format / current_date`，看不到上述工作单、candidate_id、生态名、private 路径或旧题参照。tool_profile 由运行环境配置，不靠在输入中注入私有配置文件。每次 CG、GO、A、B 都是单独会话和输出目录；A/B 是角色标签，不是两个不同模型。

## 5. Codex 工作进程

本机 CLI 0.153.4 已验证支持 `codex exec`、`--model`、`--json`、`--output-schema`、`--output-last-message`、`--cd` 和 `--skip-git-repo-check`。使用 stdin 传入拼好的提示词，记录事件流与最终结果。精确调用见[运行文档](03_runtime.md)。[官方非交互执行说明](https://learn.chatgpt.com/docs/developer-commands#codex-exec)

GPT-6 Astra 的当前标识为 `gpt-6-astra`；若以后改为直接 API 调工具，应使用 Responses API，并核对参数支持，不能照搬旧模型的 temperature/top_p 设置。[官方模型参数](https://developers.openai.com/api/docs/guides/latest-model#gpt-6-astra-update-api-and-model-parameters)

**隔离选择**：本机已有可响应的 Linux Docker 服务，可作为第一版实际读取隔离的候选。只向求解容器提供公开输入、审核过的工具配置和自己的输出卷。不要挂载研究根目录、整个用户主目录、历史 Codex 会话或 Docker socket。容器不自动等于隔离完成：还要核对外部 MCP 是否能访问私有文件、凭据如何注入、历史缓存/插件/全局指令是否带入答案。已有容器服务可用不代表镜像、模型认证和工具已打通。

构造与难度求解使用不同工具配置：构造可充分探索；难度对照优先用原文 search/fetch/PDF。若某候选确需浏览器，归入单独协议，并按相同浏览器配置重跑旧对照。新旧题交错安排，使用相同检索缓存政策，避免先测完旧题再测新题带来站点时间变化。

## 6. 父进程应执行的检查

1. **执行事实**：进程是否结束、超时/额度/工具故障、是否有最终回复、真实 model/provider 是否符合配置。不能由模型自报 status 替代。
2. **资产类型与引用**：JSON schema、必要资产是否存在、source_id 能否解析、row_key 是否有效。类型检查不证明事实正确。
3. **参考计算**：由保存源响应运行参考解，重新产出 oracle；核心计数与连接使用第二条独立核对路径。
4. **确定性评分**：独立程序解析预测，给出字段/行/顺序指标及差异；不能让生成者主观给自己打分。
5. **研究判断**：审计者核查完整性、唯一性、条件意义、捷径和难度来源；允许 reject/inconclusive，不能把缺信息补成通过。

只对本次启动的进程组做超时回收。工具成功回包或有实质输出才算进展，心跳、空事件和重复报错不应无限重置停滞时间。调用总数包含失败与重试；token 只有结束后才可见时只能事后记账，不能声称已精确控制 token。

## 7. 难度结论怎么落地

先将目标明确为：**每个保留的新底题有实证结构升级，且最终新集合在同协议 GPT-6 测试中比现有 50 底题更难；需要单题结论时另做单题对照。** 不能用平均分降低替某个容易新题背书，也不能声称每道新题都严格难于旧题中最难一道。

为每个候选在看新题筛选成绩前指定旧近邻、其中的主要对照和选择依据。用当前 GPT-6 重测旧题，不引用原论文的 GPT-5.5 等历史均值。旧题中有错配、歧义或不可复现项时，单列不能比较的原因和覆盖率；不能暗中修成另一道题后继续当原 50 题。

开发时可以用少量试次淘汰容易题；开发结束后先确定入选候选集合、确认次数、分析指标、实际目标幅度，再运行一次完整确认。建议将 Item-F1 作为主要难度指标，Row-F1 和整题正确率用于检验方向，P.O.A. 辅助解释。具体统计见[难度文档](02_difficulty.md)。

三个结论分别保存：结构升级、单题相对对照难度、集合整体难度。如果只有“新集合更难”得到支持，单题仍可为 inconclusive，不能全部填 confirmed_harder。用确认结果继续筛掉容易题或修改题面，就已经把该轮用于开发；应完整保留选择历史，最终对确定后的整个集合做新的确认，不把多次尝试中最好的一轮当最终证据。

## 8. 12 个生态的探索边界

范围沿用正式 50 题所属的 12 个生态，14 个 domain 仍保留原值。首批名额是 WQP、Water Office、CFPB、ChemExpo 各两个；其他八个生态按[站点说明](04_sites.md)逐步探索。优先级依据可验证的新状态依赖与来源可达性调整，不为了达成指定数目接受无效题。

本轮特别修正三个方向：WQP 先确定活动/站点访问/样本的身份粒度再谈完整面板；ChemExpo 先分清数据文档、UPC 产品、PUC 归属和分类方法，再谈分支计数；Water Office 先检查多站服务或HYDAT批量预取能否把动态窗口全部转成本地计算。一个现成官方批量接口如果仍要求正确选择范围和身份连接，属于合法等价解法；只有实际消除了声称关键的依赖，才反驳该难度构想。不能以“窗口未知”直接证明无法预取有限时间全集，具体依据见[站点复核](../research/site_review_2026-09-08.md)。

## 9. 提示词如何拼装

非盲阶段：共同事实与权限规则 + 当前角色提示词 + 有界工作目标 + 已复制输入资产的目录说明 + 具体完成条件 + 结果 schema。不要附带整篇历史聊天；只传当前阶段需要的信息。

盲阶段：统一求解提示词 + 一个公开题面 JSON + solver_result schema。不要传共同构造提示、旧题难度、新题来源、期望行数或裁决反馈。确认与普通难度求解用同一提示，差别只在控制端标记的轮次。

调用准备工具示例见 [scripts/README.md](../scripts/README.md)。新增[启动提示](../prompts/campaign_start.md)可给顶层 Codex 使用；它不进入盲解上下文，也不会因为被复制进文档就自动执行。

## 10. 分阶段交付

**先验证运行链路**：容器中一条已知旧题，以公开投影作为输入，打通工具、结果 schema、事件记录与评分；同时核对求解环境确实读不到私有材料。

**再完成第一题**：从 WQP 的活动/结果切片进入完整候选枚举，先查清粒度与定义，完成参考解、两种题面、独立解答和攻击。若证据不支持构想，淘汰并转 Water Office 的批量路径验证，再决定是否构造窗口题。

**然后扩展候选**：普通阶段队列、预算和恢复接入后展开首批 8 个名额。保留所有失败、修订、选择与来源问题；先估计每个接受题的实际成本，再决定扩大数量。

**最后验证难度**：相同配置重测旧 50 底题和最终新题集，做有生态控制的统计；可复现和难度结论成立后，生成与原格式兼容的 CG/GO JSONL、参考程序、证据索引与方法说明。对外发布是后续明确行动，本设计不自动上传。
